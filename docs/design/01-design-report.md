## 0. 요약: 설계의 기둥 다섯 개

1. **상태 전이는 코드가 결정하고, LLM은 제안만 합니다.** 비서실장을 포함한 모든 직원은 "구조화된 제안"만 제출합니다. 티켓 상태를 바꾸는 것은 결정적 상태기계 코드뿐입니다. 발언 횟수로 종료를 판정하던 Orkestra 문제와, 비서실장 권한 과잉 문제를 근본적으로 없애려는 구조입니다.
2. **완료는 오케스트레이터가 직접 만든 증거로만 판정합니다.**
   - diff, 경로 범위 검사, 테스트는 직원이 아니라 오케스트레이터가 깨끗한 검증 작업공간에서 직접 실행하고 결과를 저장합니다.
   - 직원의 "완료했습니다"는 상태 전이 조건에 들어가지 않습니다.
3. **원본 저장소는 반영 전까지 건드리지 않습니다.**
   - 직원은 데이터 폴더의 격리 복제본(미러)에서 만든 worktree에서만 작업합니다.
   - 원본 저장소에는 대표가 승인한 뒤에만 새 브랜치로 들어옵니다.
4. **CLI 세션은 일회용이고, 회사의 기억은 DB에 둡니다.**
   - 기본값은 실행마다 새 CLI 세션을 여는 것입니다. 연속성은 DB에서 만든 "컨텍스트 팩"으로 이어갑니다.
   - 세션 재개는 같은 실행 안의 복구에만, 명시적 세션 ID로만 합니다.
5. **PTY도, 에이전트끼리의 직접 대화도 없습니다.**
   - 세 CLI 모두 headless와 JSON 출력을 지원합니다. [사실] agy가 지원하는 것은 이번에 확인했습니다. Claude와 Codex는 M0에서 실측합니다.
   - 따라서 터미널 화면을 긁어 올 필요가 없습니다.
   - 직원 간 메시지는 DB 레코드일 뿐이고, 셸 입력으로 가는 경로가 아예 없습니다.

## 1. 핵심 가치와 사용 흐름

**핵심 가치** [제안]
여러 구독 CLI를 서로 다른 책임과 권한을 가진 직원으로 묶습니다. 그리고 증거 기반 검수와 대표 승인 게이트를 거친 변경만 프로젝트에 들어가게 합니다. 그 과정의 결정·주장·실패는 재시작과 무관하게 남습니다.

요점은 "많은 AI"가 아닙니다. **서로 다른 모델이 독립적으로 분석하고 반박하게 하고, 그 과정을 코드로 강제하며, 모든 것을 기록한다**는 것입니다.

**기본 사용 흐름**
1. 대표가 요청을 입력합니다. 예: "피로도 규칙 결정 D-12를 설계 문서에 반영해."
2. 비서실장이 **티켓 초안**을 만듭니다. 여기에는 요구사항, 완료 조건, 검증 방법, 쓰기 범위, 추천 담당자·검수자가 들어갑니다. 초안은 JSON 스키마로 검증합니다.
3. 오케스트레이터가 초안을 검증합니다. 권한 범위, 경로 잠금 충돌, 담당자와 검수자가 같은 사람인지를 봅니다. 대표 확인이 필요한 항목은 승인함으로 보냅니다.
4. 담당 직원의 사전 점검(preflight)을 통과하면 worktree를 만들고 실행합니다.
5. 제출하면 오케스트레이터가 검증합니다. 범위 검사, 보호 경로 검사, 검증 명령 실행을 합니다.
6. 검수자는 다른 모델 계열을 기본으로 합니다. 제출 시점 SHA의 읽기 전용 사본에서 요구사항별로 판정합니다.
7. 수정 요청이 오면 원 담당자가 반드시 답합니다. 수정하거나, 이유를 대고 반박합니다. 회차에 상한이 있습니다.
8. 대표 승인함에는 diff, 증거, 검수 결과, 미해결 이견이 함께 올라옵니다. 대표가 승인하면 원본 저장소에 브랜치로 반영합니다.
9. 결정 기록과 인수인계를 갱신하고 티켓을 완료합니다.

## 3. 시스템 전체 아키텍처 [제안]

```
┌──────────── 브라우저 (React 대시보드, 한국어) ────────────┐
│  REST(명령) + SSE(상태 스트림), 127.0.0.1 + 세션 토큰      │
└───────────────────────────┬───────────────────────────────┘
┌───────────────────────────▼──────── company daemon (Node/TS, 단일 프로세스) ──┐
│ server/     HTTP·SSE, 인증, Host 헤더 검증                                    │
│ core/state  티켓·실행·검수·주장·승인 상태기계 (순수 함수, LLM 없음)            │
│ core/policy 역할 계약 → CLI 플래그, 범위 검사, 승인 바인딩                     │
│ scheduler/  의존성·경로잠금·사용량풀·예산 기반 디스패치                        │
│ context/    컨텍스트 팩 빌더 (결정·주장·인수인계·문서권한규칙)                  │
│ runner/     프로세스 감독: 출력→파일, tail, heartbeat, 트리 종료, 고아 복구     │
│ adapters/   claude | codex | agy (+fake)                                    │
│ workspace/  미러 저장소, worktree, 경로잠금, 통합(반영)                        │
│ evidence/   diff·범위검사·검증명령 실행·증거 매니페스트                        │
│ store/      SQLite(WAL) + 해시체인 이벤트 로그 + 파일 산출물                   │
└──────────┬──────────────────────────┬─────────────────────────────┬──────────┘
   child: claude.exe / node codex.js / agy   child: 검증 명령(dotnet test 등)   git.exe
   (출력은 파일로, detached)                  (argv 배열, shell 없음)
```

**기술 방향 검토**
- **유지:** TypeScript, Node, React, SQLite, worktree, SSE.
- **SQLite 라이브러리:** `better-sqlite3`가 동기식이고 Windows 사전 빌드 바이너리가 있습니다. 이 PC의 Node는 v25.1.0이라 내장 `node:sqlite`도 쓸 수 있습니다. 내장 쪽이 네이티브 의존성을 없애 주지만, 안정성 등급을 확인한 뒤 정합니다. [미정: M0]
- **WebSocket은 불필요합니다.** 서버에서 보내는 상태 스트림은 SSE로 충분하고, 명령은 REST로 보냅니다.
- **node-pty는 쓰지 않습니다.** 네이티브 빌드가 필요하고 화면 스크래핑이 필요 없기 때문입니다.
- **ORM 없이** 평문 SQL, 마이그레이션 파일, zod 스키마로 갑니다.
- **데스크톱 패키징(Tauri·Electron)은 MVP 이후**로 미룹니다.
- **Go·Rust 단일 바이너리**는 Windows 프로세스 관리와 배포에서 유리합니다. 그래도 UI와 한 언어로 통일하는 이점이 커서 TS를 유지합니다.

## 4. 프로세스·컴포넌트 책임 경계

| 주체 | 할 수 있는 일 | 할 수 없는 일 |
|---|---|---|
| **대표 (사람)** | 모든 승인, 역할 계약 변경, 결정 확정 | — |
| **오케스트레이터 (코드)** | 상태 전이, 디스패치, 검증 명령 실행, worktree 생성, 승인 후 반영 | 승인 없이 게이트 작업 실행, 게임 규칙·수치 결정 |
| **비서실장 (LLM 직원)** | 읽기 전용 조회, 티켓 초안 작성, 배정 제안, 보고서 종합 초안 작성, 상신 초안 작성 | 저장소 쓰기, 자기 결과 승인, 권한 변경, 감사 로그 접근, 검증 명령 실행 |
| **담당 직원 (LLM)** | 자기 티켓 worktree의 쓰기 범위 안에서 수정, 역할에서 허용한 명령 실행, 구조화 보고 제출 | 다른 worktree, 원본 저장소, DB, 자격증명 경로 접근. 자기 검수 |
| **검수 직원 (LLM)** | 제출 SHA의 읽기 전용 사본 검사, 요구사항별 판정, 주장 등록 | 담당자 worktree 수정, 오케스트레이터 검증 결과 무시 |
| **문서·기록 직원 (LLM)** | 결정·인수인계 초안 작성, 문서 담당 경로 수정(티켓 경유) | 결정 확정. 확정은 대표만 합니다. |

**원칙**
- LLM 출력이 상태를 바꾸는 유일한 통로는 `submit(runId, schemaValidJson)`입니다.
- 무엇을 하든 상태기계의 가드를 통과해야 합니다.

## 5. CLI 어댑터 인터페이스 [제안]

```ts
interface CliAdapter {
  kind: 'claude' | 'codex' | 'agy' | 'fake';
  locate(): Promise<ExecutableInfo>;          // PATHEXT·.exe/.cmd/.ps1 판별, .cmd shim → 실제 node 스크립트 해석
  version(): Promise<string>;
  preflight(ws: WorkspaceRef): Promise<PreflightReport>; // 로그인·headless·JSON·sandbox·쓰기/읽기 경계 카나리 테스트
  capabilities(): CapabilityMatrix;           // M0 실측값, 버전별 캐시
  buildInvocation(req: RunRequest, contract: RoleContract): Invocation; // argv 배열 + stdin 프롬프트 + env
  parseEvent(line: string): AdapterEvent | null; // JSONL → 정규화 이벤트 (UTF-8 디코딩 끝난 줄만 입력)
  finalize(runDir: string): RunOutcome;       // 결과 이벤트·nonce·세션ID·보고서 파일 교차 확인
  classifyFailure(o: RawOutcome): FailureClass; // auth_required | usage_limit | timeout | crash | schema_invalid | policy_violation | unknown
  resumeArgs?(cliSessionId: string): string[]; // ID 지정만. --continue/--last 금지
}
```

**CLI별 매핑**

| 항목 | Claude Code | Codex | Antigravity (agy) |
|---|---|---|---|
| headless | `-p` (stdin 입력) | `exec` (stdin 입력) | `-p` [사실] |
| 구조화 출력 | `--output-format stream-json` | `--json`, `--output-last-message`, `--output-schema` | `--output-format json\|stream-json`, `--json-schema` [사실] |
| 재개 | `--resume <id>` | `exec resume <id>` | `--conversation <id>` [사실]. `--continue` 사용 금지 |
| 권한 | `--permission-mode`, `--allowedTools`/`--disallowedTools`, `--add-dir` | `--sandbox read-only\|workspace-write`, `-a never`, `-C` | `--sandbox`, `--dangerously-skip-permissions`만 확인됨 [사실]. 세밀한 제어는 없음 |
| 시간 제한 | 자체 타이머 | 자체 타이머 | `--print-timeout` (기본 5분) [사실] |
| 인증 누락 시 | [미정: M0] | [미정: M0] | TTY가 없으면 `authentication required`로 종료 [사실] |

Claude와 Codex 칸의 플래그는 웹 문서와 기존 지식에 근거합니다. 설치된 버전에서 M0에 실측합니다. 사용자 전역 설정·플러그인·훅이 직원에게 새어 들어가지 않는지(`--setting-sources`, `--strict-mcp-config` 등)도 M0에서 확인합니다.

**Windows 실행 규칙** [제안]
- `shell: true`는 쓰지 않습니다.
- `.cmd`/`.bat` shim은 Node 보안 패치(2024) 이후 shell 없이 spawn하면 거부됩니다. 그래서 shim을 해석해 `node.exe <실제 스크립트>`로 직접 실행합니다. shim 해석은 M0에서 확인합니다.
- `.ps1`은 실행하지 않습니다. 사전 점검에서 실행 정책만 보고합니다.
- **프롬프트는 argv가 아니라 stdin**으로 넘깁니다. argv 32K 제한과 인용 문제를 피하기 위해서입니다.
- **stdout과 stderr는 각각 파일로 보냅니다.** 자식 프로세스는 detached로 띄우고, 데몬은 파일을 tail합니다. 데몬이 죽어도 출력이 남습니다.
- UTF-8은 `TextDecoder(stream:true)`로 푼 다음에 줄을 나눕니다. 바이트 단위로 자르지 않습니다.
- 종료는 `taskkill /T /F /PID`로 프로세스 트리째 합니다. PID를 재사용한 다른 프로세스를 잘못 죽이지 않도록 프로세스 생성 시각을 대조합니다.

**성공 판정은 조건 5개를 모두 만족해야 합니다.** (exit code 0만으로는 성공이 아닙니다)
1. 프로세스가 종료했습니다.
2. 최종 결과 이벤트가 있습니다.
3. 보고서 JSON이 스키마 검증을 통과합니다.
4. 이번 실행의 **nonce**가 보고서에 들어 있습니다.
5. 세션 ID가 기록과 일치합니다.

같은 runId로 결과가 두 번 들어오면 두 번째는 무시합니다(멱등 처리).

## 7. 업무 상태기계 [결정 + 제안]

**기본 흐름** [결정]
`접수 → 분석 → 대기 목록 → 배정 → 작업 중 → 검수 중 → 수정 요청 → 재검수 → 대표 승인 대기 → 반영 → 완료`

**제안하는 수정**
- `작업 중`과 `검수 중` 사이에 자동 단계 **`제출 검증`**을 추가합니다. 오케스트레이터가 실행하는 단계입니다.
- `재검수`는 `검수 중`에서 round가 2 이상인 경우로 표현합니다.
- 추가 상태 중 5개(사용자 결정 필요, 선행 업무 대기, 사용량 한도 대기, 권한 승인 필요, 보류)는 **직교하는 보류(hold) 플래그**로 둡니다. 보류가 풀리면 원래 상태로 돌아가야 하므로 `resumeTo`를 저장합니다.
- `실패`와 `취소`는 종료 상태입니다.

| 전이 | 주체 | 가드 (코드로 검사) |
|---|---|---|
| 분석 → 대기 목록 | 오케스트레이터 | 요구사항마다 `evidenceType`이 있음. 완료 조건·검증 방법·쓰기 범위가 있음. 보호 경로와 겹치면 권한 승인 필요 |
| 대기 목록 → 배정 | 비서실장 제안 + 코드 | 담당자와 검수자가 다른 사람. (기본) 다른 CLI 계열. 역할 계약이 쓰기 범위를 허용. 두 직원 모두 최근 사전 점검 통과 |
| 배정 → 작업 중 | 코드 | 선행 업무 완료. **경로 잠금 획득**(활성 티켓과 겹치지 않음). worktree 준비. 사용량 풀 여유 있음 |
| 작업 중 → 제출 검증 | 코드 | 실행 성공 판정 조건 5개 충족 |
| 제출 검증 → 검수 중 | 코드 | 변경 경로가 쓰기 범위 안. 보호 경로 해시 불변. 저장소 ref 스냅샷 불변(담당 브랜치 제외). **검증 명령을 깨끗한 검증 worktree에서 오케스트레이터가 실행**하고 결과 저장. 모든 요구사항에 대한 자기 보고가 있음 |
| 제출 검증 → 수정 요청 | 코드 | 검증 명령 실패, 또는 보고 누락 |
| 제출 검증 → 보류(권한 승인 필요) | 코드 | 범위 밖 쓰기, 또는 ref 변경. 결과는 격리하고 대표가 판단 |
| 검수 중 → 수정 요청 | 검수자 | 판정 스키마가 유효하고, 반대하는 요구사항 ID와 근거가 있음 |
| 검수 중 → 대표 승인 대기 | 검수자 + 코드 | 모든 요구사항이 `met`이고 증거 ID가 달려 있음. 오케스트레이터 검증이 통과한 상태. 미해결 주장은 승인함에 함께 표시(숨기지 않음) |
| 수정 요청 → 작업 중 | 코드 | round < 최대값(기본 3). 초과하면 사용자 결정 필요로 보류 |
| 대표 승인 대기 → 반영 | 대표 | 승인이 (티켓, headSha, diffHash, baseSha)에 묶임. 하나라도 바뀌면 승인 무효 |
| 반영 → 완료 | 코드 | 기준 브랜치가 움직였는지 확인하고, 움직였으면 병합 결과로 검증을 다시 실행. 반영 커밋 SHA 기록. 결정의 `reflectedIn` 갱신 |

**실행(Run) 상태기계**
`준비 → 기동 → 실행 중 → 종료 → 수거(성공 | 분류된 실패)`
재시작 때 발견한 실행 중 프로세스는 `고아`로 표시합니다(10절).

**검토·토론형 티켓 (인사이트 3)**
1. **블라인드 분석:** 같은 입력을 여러 직원에게 병렬로 줍니다. 컨텍스트 팩에는 다른 직원의 결과를 넣지 않습니다. 결과 파일은 직원이 읽을 수 없는 데이터 폴더에 둡니다.
2. **주장 등록:** 결과를 스키마 강제로 주장 원장에 올립니다.
3. **교차 검토:** 주장마다 검토자를 배정하고, 4종 판정 중 하나를 받습니다.
4. **재답변:** 동의가 아닌 판정을 받은 **모든 주장에 원 작성자가 답하기 전에는 다음 단계로 넘어가지 않습니다.**
5. **종합:** 종합 결과에 모든 주장 ID와 최종 상태가 들어갔는지 코드로 검증합니다. 빠진 주장이 있으면 거부합니다. 다수결 표현은 쓰지 않습니다.
6. **상신:** 미해결 주장은 대표 승인함으로 올립니다.

**반복 예산**
- 주장당 반박은 1회, 재답변도 1회입니다. 이후에도 남은 이견은 대표에게 올립니다.
- 같은 주장이 반복되는지는 텍스트 정규화 해시로 판정합니다.

## 8. 권한과 승인 모델 [제안]

**권한을 거는 세 가지 층**

| 층 | 장치 | 한계 |
|---|---|---|
| ① 사전 제한 | 역할 계약을 CLI 플래그로 변환합니다. Claude는 도구 허용·거부 목록, Codex는 sandbox 모드, agy는 `--sandbox`. 네트워크는 끄는 것이 기본입니다. | CLI마다 강도가 다릅니다. agy는 세밀하게 제어할 수 없습니다. |
| ② 사후 검증 | 변경 경로 ⊆ 쓰기 범위, 보호 경로 해시, 원본·미러 ref 스냅샷, 원본 저장소 `git status` 불변 | 작업공간 밖의 임의 경로에 쓴 것은 완전히 탐지할 수 없습니다. |
| ③ 결과 격리 | 위반한 제출은 반영 경로에서 제외하고 대표에게 올립니다. | — |

**승인 객체**
- `approval`에는 `subjectHash`가 들어갑니다. 해시 대상은 종류, argv, cwd, worktree headSha, diffHash입니다.
- **1회용**이고 만료 시각이 있습니다.
- 대표만 만들 수 있습니다. UI 세션 토큰에서만 발급하고, LLM이 부르는 API에는 발급 경로가 없습니다.

**비서실장 제한** [결정 확장]
- 자기가 만든 티켓 초안이 쓰기 범위를 확대하면 대표 승인이 필요합니다.
- 권한·계약 API를 부를 수 없습니다.
- 감사 로그(event)와 증거에는 읽기 권한도 선택적으로만 줍니다. 쓰기는 없습니다.

**실행 중 권한 요청 → GUI 승인** [결정 + 제안]
- **흐름**
  1. 직원 CLI가 허락을 구하면 어댑터가 가로챕니다.
  2. 승인함과 실시간 알림에 요청을 띄웁니다.
  3. 대표가 허용·거부하는 동안 해당 실행은 대기합니다.
- **대기 시간 제한:** 기본 10분입니다. 그 안에 답이 없으면 거부로 처리하고, 티켓을 `권한 승인 필요` 보류로 바꿉니다. 조용히 넘어가지 않습니다.
- **승인 범위 선택지**
  - 이번 한 번만
  - 이 티켓 동안 같은 명령 허용
- **CLI별 가로채기 수단** (M0에서 실측)

| CLI | 가로채기 수단 | 비고 |
|---|---|---|
| Claude | `--permission-prompt-tool`: 권한 판단을 Agent Company가 제공하는 MCP 도구에 넘김 | 가능성 높음 |
| Codex | `codex app-server`(JSON-RPC)의 명령 실행·패치 승인 요청 | 가능성 높음 |
| agy | 가로채기 수단 미확인 | 없으면 실행 전 정한 등급으로만 동작하고, 도중 승인은 불가 |
| 공통 대안 | ACP(Agent Client Protocol)의 권한 요청 기능 | 후보 |

**접근 등급 (직원별 선택)** [결정 + 제안]
- CLI마다 다른 권한 체계를 공통 4단계로 묶습니다.
- 어떤 CLI가 특정 단계를 제대로 구현할 수 없으면(M0 결과) 그 단계는 선택지에서 비활성화합니다.

| 등급 | 뜻 | Claude | Codex | agy |
|---|---|---|---|---|
| 1 읽기 전용 | 파일 읽기만 | 읽기 도구만 허용 | `--sandbox read-only` | `--sandbox` (M0 확인) |
| 2 쓰기 + 명령은 매번 승인 | 작업공간 파일 수정은 자동, 명령 실행은 GUI 승인 | 편집 자동, 나머지는 GUI 승인 | `workspace-write`, 명령은 GUI 승인 | 미확인 |
| 3 쓰기 + 허용 목록 명령 자동 | 등급 2 + 대표가 정한 명령은 자동 | 허용 목록 | 허용 목록 | 미확인 |
| 4 전체 자동 (위험) | 모든 요청 자동 허용 | `bypassPermissions` | `danger-full-access` | `--dangerously-skip-permissions` |

- 등급 4는 선택할 때 경고를 띄우고 대표 승인을 받습니다. 기본값은 등급 2입니다.
- 어떤 등급에서도 사후 검증(범위·보호 경로·ref 검사)은 그대로 적용합니다.

**앱 전용 CLI 프로필** [제안, 대표 선택 필요]
- 목표: 대표님의 개인 설정(전역 지시문·플러그인·훅·MCP)이 직원에게 섞이지 않게 합니다.

| 방식 | 방법 | 격리 | 비용 |
|---|---|---|---|
| **A. 별도 프로필 폴더 (권장)** | 직원 CLI를 실행할 때만 설정 폴더 위치를 바꿉니다. Claude는 `CLAUDE_CONFIG_DIR`, Codex는 `CODEX_HOME`, agy는 M0에서 확인 | 완전 | 앱 프로필에서 **CLI마다 로그인을 1회 새로** 해야 합니다 |
| B. 기존 프로필 + 차단 플래그 | 기존 설정을 쓰되 `--setting-sources`, `--strict-mcp-config` 등으로 일부를 끕니다 | 부분적. 무엇이 새는지 M0에서 확인 | 추가 로그인 없음 |

- 방식 A의 프로필 폴더는 `C:\AgentCompany\profiles\<cli>\`에 둡니다.
  - 안에는 CLI가 스스로 관리하는 로그인 파일이 생깁니다. **Agent Company는 이 파일을 읽지 않습니다.**
  - 위치는 설치 정보 화면에 표시합니다.
  - 제거할 때 로그인 정보를 지울지 남길지 묻습니다.
- 대표님의 기존 설정 폴더(`~/.claude`, `~/.codex`)는 어느 방식에서도 건드리지 않습니다.

**자격증명 경로 차단**
`~/.claude`, `~/.codex`, agy 설정 폴더, `%APPDATA%` 자격증명 폴더를 모든 직원 계약의 거부 목록에 기본으로 넣습니다.

## 9. worktree 격리와 병합 전략 [제안]

- **미러 저장소:** `<data>/projects/<pid>/mirror`에 원본을 로컬 복제합니다(`git clone --local`).
  - 같은 볼륨이면 객체를 하드링크하므로 용량이 작습니다. 위치와 크기는 UI에 항상 표시합니다(인사이트 16).
  - **미러에는 origin 원격을 두지 않습니다.** 그래서 직원이 push할 대상이 없습니다.
- **티켓 worktree:** `<data>/projects/<pid>/wt/<ticketId>`, 브랜치는 `ac/<ticketId>`입니다. 수정 회차가 바뀌어도 같은 worktree를 계속 씁니다.
- **검수:** 제출 SHA로 **분리(detached) 읽기 전용 worktree**를 따로 만듭니다. 검수자는 sandbox를 read-only로 둡니다.
- **검증:** 제출 SHA로 **깨끗한 검증 worktree**를 만들고, 오케스트레이터가 argv 배열로 명령을 실행합니다. 담당자 worktree가 더러운 상태에서 "내 환경에선 됨"이 되는 것을 막습니다.
  - Unity 티켓은 Library를 보존해야 하므로, 검증 worktree 하나를 재사용합니다(`checkout <sha>` 후 `clean`).
- **경로 잠금:** 티켓의 쓰기 범위 glob을 디렉터리 접두사 기준으로 보수적으로 비교합니다. 겹치면 동시에 배정하지 않습니다. 공통 파일은 선행 티켓으로 분리합니다.
- **반영(통합)** — 대표 승인 뒤에만 합니다.
  1. 원본 저장소의 현재 기준 SHA를 확인합니다.
  2. 미러에서 `ac/<ticketId>`를 기준 위에 병합한 결과로 검증을 다시 실행합니다.
  3. **원본 저장소에 `ac/<ticketId>` 브랜치로 fetch합니다.** 두 방식 모두 여기까지는 같습니다.
  4. 이후 동작은 프로젝트 설정 `integrationMode`에 따라 갈립니다. 승인함에서 티켓별로 바꿀 수도 있습니다. **[결정]**
     - **`manual`:** 여기서 멈춥니다. 대표가 직접 병합합니다.
     - **`auto_after_approval`:** 승인 항목이 "승인 + 병합"일 때만 오케스트레이터가 병합합니다. 이 승인은 병합 대상 SHA에 묶입니다. 순서는 이렇습니다.
       1. 미러에서 기준 브랜치에 `--no-ff`로 병합한 커밋을 만들고 검증을 다시 실행합니다.
       2. 원본 저장소에서 기준 브랜치가 **체크아웃되어 있지 않으면**, ref를 fast-forward로만 갱신합니다.
       3. 기준 브랜치가 **체크아웃되어 있으면**, 작업 트리가 깨끗할 때만 `git merge --ff-only`를 실행합니다. 대표의 작업 파일을 덮어쓰지 않기 위해서입니다.
       4. 병합 전 기준 SHA를 기록합니다. 되돌릴 때는 `git revert`를 쓰며, 이것도 대표 승인이 필요합니다.
     - **자동 병합 불가 → 수동으로 강등:** 아래 경우에는 병합하지 않고 `manual`로 바꾼 뒤 대표에게 알립니다.
       - fast-forward가 불가능한 경우
       - 작업 트리가 더러운 경우
       - 재검증에 실패한 경우
- **정리:** 완료·취소된 티켓 중 worktree가 깨끗한 것만 정리 후보로 올립니다. 대표 일괄 승인 후 삭제합니다. 더럽거나 증거가 남아 있으면 삭제하지 않습니다.
- 경로 길이 문제를 피하려고 **데이터 폴더를 짧은 경로로** 둡니다(예: `C:\AgentCompany`). `core.longpaths`는 미러의 로컬 설정에만 켭니다. 전역 git 설정은 건드리지 않습니다.

## 10. 프로세스 종료·재시작 복구 구조 [제안]

- **먼저 기록하고 나중에 실행합니다(write-ahead).** 실행 레코드(nonce, 기대 산출물, 컨텍스트 팩 해시)를 커밋한 **뒤에** 프로세스를 띄웁니다. 띄운 직후 pid와 생성 시각을 기록합니다.
- 출력은 파일로 쓰고 detached로 돌리므로, **데몬이 죽어도 CLI는 계속 돌고 출력도 남습니다.**
- **데몬이 재시작할 때 순서**
  1. 이벤트 해시 체인을 검증합니다.
  2. `실행 중`인 실행을 찾아 **pid와 생성 시각이 모두 맞는지** 확인합니다.
     - 살아 있으면 출력 파일 tail을 재개합니다.
     - 죽었으면 출력 파일을 `finalize()`합니다.
  3. 판정이 불가능하면 `고아`로 표시하고 대표에게 보여줍니다. **자동으로 성공 처리하지 않습니다.**
  4. worktree 상태(HEAD, dirty)를 DB 기록과 대조합니다. 다르면 보류 상태로 둡니다.
- **세션 재개 규칙 (인사이트 11):** 다음이 모두 일치할 때만 `--resume <id>` 계열을 씁니다. 하나라도 다르면 새 세션을 열고 컨텍스트 팩을 넣습니다.
  - 세션 레코드의 (employee, ticket, worktree 경로, CLI 종류·주 버전)
  - CLI 출력에 찍힌 세션 ID
- **PC 재시작:** 데몬은 자동으로 실행되지 않습니다. 대표가 켜면 위 복구 절차를 거쳐 **"복구 보고"** 화면을 먼저 보여줍니다.

## 11. 사용량 한도와 실패 처리 [제안]

**실패 분류와 처리**

| 분류 | 처리 | 자동 재시도 |
|---|---|---|
| 기동 실패, 일시 오류 | 대기 후 재시도 | 최대 1회 |
| 시간 초과 | 프로세스 트리 종료, 부분 결과 보존 | 1회, 이후 보류 |

| 스키마 불일치 | "형식만 다시 내라"는 요청 1회 | 1회 |
| 정책 위반 | 결과 격리, 권한 승인 필요로 보류 | 안 함 |
| 알 수 없음 | 실패로 분류하고 원문 보존 | 안 함 |

**예산** (티켓마다 설정, 기본값은 [미정])
- 최대 실행 수 6, 수정 회차 3, 실행당 시간 30분, 일일 사용량 풀별 실행 수

**진전 없음 감지** — 아래에 해당하면 즉시 사용자 결정 필요로 보류합니다.
- 연속된 제출의 diffHash가 같음
- 같은 테스트 실패 시그니처가 반복됨
- 같은 주장 해시가 반복됨

최대 반복에 도달하면 **실패나 보류로만** 끝납니다. 성공으로 처리하지 않습니다.

## 14. 테스트와 검증 전략 [제안]

- **fake CLI:** 시나리오 JSON에 따라 JSONL을 내보내는 가짜 실행 파일입니다. 다음 경우를 재현합니다.
  - 정상 완료
  - 무응답(hang)
  - 스트림 도중 종료
  - **UTF-8 멀티바이트 경계 분할**
  - 결과 중복
  - nonce 누락이나 불일치
  - 허위 완료(보고는 성공인데 diff가 없음)
  - 범위 밖 쓰기
  - 사용량 한도 메시지
  - 인증 필요
- **장애 주입:** 상태 전이의 모든 지점에서 데몬을 강제 종료하고 재시작합니다. 확인할 것은 두 가지입니다.
  - 상태·worktree·증거가 사라지지 않는지
  - 성공으로 잘못 처리되지 않는지
- **상태기계 속성 테스트:** 임의의 이벤트 순서를 넣어도 다음 불변식이 지켜지는지 봅니다.
  - 대표 승인 없이 `반영`에 도달하지 않음
  - 담당자와 검수자가 같지 않음
  - 보류가 풀리면 원래 상태로 복귀
- **Windows 전용:** 공백·한글이 들어간 경로, 260자를 넘는 경로, `.cmd` shim, 실행 정책 Restricted, 콘솔 코드페이지 949
- **보안:** 메시지 본문에 `; & | $() ` ANSI 이스케이프를 넣어도 어떤 프로세스의 argv·stdin에도 셸 해석 없이 전달되는지 봅니다. 컨텍스트 팩에서는 데이터 영역에만 들어가야 합니다. DNS 리바인딩(Host 헤더 불일치 시 거부)과 CSRF도 검사합니다.
- **실제 CLI 계약 테스트:** 사용량을 쓰므로 수동으로 트리거하고, 버전마다 1회 실행합니다.

## 맺음말: 10개 질문에 대한 답

1. **왜 새로 만드는가**
   기존 도구는 셋 중 하나에 그칩니다. 실행 플랫폼(OpenHands·wmux), 회의 도구(Crucible), 일회성 생성(MetaGPT)입니다. "상태기계가 강제하는 검수·반박 + 증거 기반 완료 + 대표 승인 게이트 + 영속 결정 원장"을 구독 CLI 위에서 Windows 네이티브로 제공하는 도구는 없습니다. [조사 기반 판단]

2. **최소 차별점**
   ① LLM이 아닌 코드가 전이를 판정합니다. ② 오케스트레이터가 직접 만든 증거만 인정합니다. ③ 원본 저장소는 승인 전까지 건드리지 않습니다. ④ 주장·결정은 상태와 함께 원장에 남습니다.

3. **"계속 일한다"를 시스템 상태로 표현하는 방법**
   회사 = DB 안의 (티켓 그래프 + 보류 사유와 resumeTo + 결정 원장 + 세션·worktree 바인딩 + 이벤트 로그)입니다. 프로세스가 계속 도는 것이 연속성이 아닙니다. **어느 시점에 켜도 "다음에 할 일"을 코드가 계산할 수 있으면** 연속성이 있는 것입니다.

4. **직원이 정말 자기 할 일을 가진다는 강제**
   - 직원 = 역할 계약 버전 + 업무함(배정된 티켓) + 사용량 풀입니다.
   - 계약 밖의 티켓은 배정이 거부됩니다.
   - 티켓이 없는 직원은 실행되지 않습니다. 실행은 반드시 티켓에 묶입니다.
   - 실행 결과는 그 티켓의 스키마로만 받습니다.

5. **허위 완료 차단**
   - 완료 전이의 가드는 오케스트레이터 증거로만 판정합니다. diff, 범위 검사, 검증 명령 종료 코드·테스트 수, nonce가 그 증거입니다.
   - 요구사항마다 필요한 증거 등급이 있어서, 모형이나 정적 검사로 런타임 요구를 채울 수 없습니다.
   - 그다음 다른 계열 검수자가 보고, 대표가 승인합니다.

6. **재시작 후에도 회사가 존재한다는 검증**
   - 장애 주입 테스트로 봅니다. 모든 전이 지점에서 데몬을 강제 종료하고 재시작합니다.
   - 이벤트 해시 체인이 유효하고, 티켓·worktree·증거가 보존되고, 고아 실행이 성공으로 처리되지 않으면 통과입니다.
   - E2E 시나리오 안에서 실제로 PC를 재시작하는 단계도 넣습니다.

7. **인증정보를 읽지 않는 방법**
   - 공식 실행 파일을 자식 프로세스로 띄우고, 사용자 환경변수를 그대로 물려줍니다. CLI는 자기 캐시 자격증명을 스스로 씁니다.
   - 오케스트레이터는 자격증명 파일을 열지 않고, 토큰도 저장하지 않습니다.
   - 로그인 여부는 공식 상태 명령이나 최소 프로브 실행의 결과로만 판정합니다.
   - agy는 "공식 바이너리를 자식 프로세스로 headless 실행하며 캐시된 자격증명을 쓰는 것은 지원되는 워크플로"라는 포럼 답변이 있습니다. [사실: 포럼 답변이며 공식 문서는 아님] 토큰 추출이나 직접 API 호출은 지원되지 않습니다.
   - Claude `-p`는 현재 구독 사용량에서 차감됩니다. [사실: 정책 변경이 보류된 상태]

8. **MVP에서 절대 만들지 않을 것**
   17절 목록 전체입니다. 특히 PTY, 에이전트 직접 대화, push·병합 자동화, 토큰 저장, 직원이 직원을 생성하는 구조는 넣지 않습니다.

9. **종단간 시나리오** — **[결정]** Adventurer Manager는 보류하고 **샘플 저장소**로 검증합니다.
   - 샘플 저장소 구성
     - 작은 TypeScript 라이브러리와 테스트
     - 담당 문서 구조가 있는 `docs/`
     - 보호 경로 1개
   - 직원은 대표가 구성한 2–4명으로 실행합니다.
   - **A. 코드 (필수)**
     1. 기능 티켓을 만듭니다.
     2. 구현 직원이 수정합니다.
     3. **결함 주입:** 테스트는 실패하는데 "완료했습니다"라고 보고합니다. 오케스트레이터 검증에서 거부되는지 확인합니다.
     4. **결함 주입:** 쓰기 범위 밖 파일을 수정합니다. 결과가 격리되는지 확인합니다.
     5. 수정 후 다른 직원이 검수해 통과시킵니다.
     6. 수정 도중 **데몬을 강제 종료하고 PC를 재시작**한 뒤 복구합니다.
     7. 대표가 승인합니다. `manual`과 `auto_after_approval` 두 방식을 각각 한 번씩 반영합니다.
   - **B. 문서 반영**
     1. 대표가 결정을 확정합니다.
     2. 담당 직원이 결정 목록만 갱신합니다(결함 주입).
     3. 검수자가 본문 미반영을 탐지합니다.
     4. 담당 직원이 수정하고 재검수를 통과합니다.
     5. 결정의 `reflectedIn`에 반영 위치를 기록합니다.
   - **C. 검토형**
     1. 문서 하나를 활성 직원들이 블라인드로 분석합니다.
     2. 주장 등록 → 교차 판정 → 재답변 순서로 진행합니다.
     3. 미해결 주장 1건을 대표에게 상신합니다.
   - **성공 기준**
     - 원본 저장소의 변경은 승인된 브랜치나 병합 커밋뿐입니다.
     - 모든 전이가 이벤트 로그에 남아 있습니다.
     - 허위 완료나 범위 밖 수정이 하나도 반영되지 않았습니다.
     - 재시작 후 같은 티켓이 같은 상태에서 이어집니다.

10. **실패 시 원상복구**
    - **원본 저장소:** 반영 전에는 변경이 없습니다. 반영된 것은 새 브랜치뿐이므로, 대표 승인 후 브랜치를 삭제하거나 병합 커밋을 revert하면 됩니다. 반영할 때 기준 SHA와 ref 스냅샷을 기록해 둡니다.
    - **사용자 환경:** 전역 git·CLI 설정·서비스·예약 작업·자동실행을 전혀 건드리지 않습니다. 따라서 원상복구는 데이터 폴더 하나를 처리하는 일입니다.
    - **제거 절차 (`uninstall`)**
      1. 실행 중인 프로세스를 종료합니다.
      2. 미커밋 worktree를 경고합니다.
      3. 데이터 폴더를 압축해 보관합니다(복구 가능).
      4. 폴더를 삭제합니다.
      5. 잔여물을 검사합니다.
